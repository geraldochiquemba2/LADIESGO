  Framework: Hono
  Banco: D1 (Neon HTTP via makeSql)
  Autenticação: JWT HS256 via WebCrypto, PBKDF2-SHA256 para senhas
  Rate limiting: 100 req/min por IP (memória por isolate)
  Guest login: throttle dedicado, 15 por hora por IP (escreve no D1)
  Comissão: 14% (COMMISSION_RATE = 0.14)
  Limite viagens negativas: 3 (NEG_TRIP_LIMIT), depois walletBlocked
  TURN/ICE: fallback openrelay.metered.ca (demo) se não houver METERED_DOMAIN

2.3 WebSockets (Durable Objects)

  - /api/v1/drivers/live-geo -> DRIVERGEO (GPS da motorista, memória)
  - /api/v1/trips/requests-live -> REQUESTSHUB (pedidos recebidos)

2.4 Server.js local (mock para desenvolvimento)

  Oferta sequencial: 15s por motorista, mais próxima primeiro
  Login mock: admin 999999999/1234567890, qualquer 9XX XXX XXX com senha ≥4

3.1 cloudflare — Descoberta de produtos e limites
  O QUE FAZ: Ajuda a escolher produtos Cloudflare para cada necessidade.
  APLICAÇÃO NO LADIESGO:
    - Frontend estático -> Pages (banda ilimitada, já em uso)
    - API backend -> Workers (100k requests/dia, já em uso)
    - Banco -> D1 (100k writes/dia, 5M reads/dia, já em uso)
    - Cache de categorias -> KV (não está a ser usado para categorias)
    - Fotos de perfil -> R2 (não está a ser usado; fotos vão no D1 via data URL)
    - WebSockets -> Durable Objects (já em uso para 3 hubs)
  O QUE SE ALCANÇA: Arquitetura já está correta, mas fotos no D1 consomem
  writes preciosas. Mover para R2 pouparia ~100k writes/dia.

3.2 wrangler — Deploy e gerenciamento de Workers, D1, KV, R2
  O QUE FAZ: CLI para deploy, migrations D1, gerenciamento de recursos.
  APLICAÇÃO NO LADIESGO:
    - wrangler.jsonc existe em webapp/ (name="taxiapp-web")
    - Necessário para deployar o Worker da API (index.ts)
    - `wrangler d1 migrations apply` para migrations incrementais
    - `wrangler kv:key put` para cache de categorias
    - `wrangler r2 bucket put` para fotos de perfil
  O QUE SE ALCANÇA: Deploy controlado da API sem tocar na conta esgotada.

3.3 cf-cli — CLI da Cloudflare (`cf` vs `wrangler`)
  O QUE FAZ: Comandos gerais (contas, domínios, DNS).
  APLICAÇÃO NO LADIESGO:
    - Trocar entre contas (antiga ladiesgo-ao vs nova ladiesgo-angola)
    - Sem usar `wrangler logout` (revoga o token — regra do AGENTS.md)
    - Configurar DNS se houver domínio personalizado
  O QUE SE ALCANÇA: Gestão de contas sem perder autenticação.

3.4 durable-objects — Coordenação stateful, WebSockets, SQLite, alarms
  O QUE FAZ: Objetos duráveis com estado, WebSockets, SQLite embarcado.
  APLICAÇÃO NO LADIESGO (JÁ EM USO, MAS PODE OTIMIZAR):
    - TRIPPUSH: estado da viagem ao vivo (/api/v1/trips/:id/live)
    - DRIVERGEO: GPS da motorista em memória (0 writes D1 por ping)
    - REQUESTSHUB: pedidos recebidos (/api/v1/trips/requests-live)
  VANTAGEM CRÍTICA: Mensagens WebSocket NÃO contam como requests do Worker
  (contam no DO a 20:1). O GPS da motorista enviado a cada 30s via WebSocket
  poupa writes D1 e requests Worker.
  O QUE SE ALCANÇA: Rastreamento ao vivo sem esgotar o limite de 100k
  Worker requests/dia. O DO já está implementado no worker (index.ts
  linhas 870-908).

3.5 agents-sdk — Agentes de IA com estado, agendamento, RPC, MCP
  O QUE FAZ: Agentes de IA com memória, agendamento, chamadas de função.
  APLICAÇÃO NO LADIESGO:

    - Agente de atendimento automático via WhatsApp (dúvidas comuns)
    - Agente de dispatch auxiliar (sugerir motorista mais próxima)
  O QUE SE ALCANÇA: Monitoramento proativo antes de esgotar quota
  (evitar erro 7500/1027).

3.6 workers-best-practices — Workers prontos para produção
  O QUE FAZ: Boas práticas para Workers eficientes e seguros.
  APLICAÇÃO NO LADIESGO:
    - Manter Worker leve (<10ms CPU time por request, limite free)
    - Evitar chamadas externas síncronas no caminho crítico (Nominatim)
    - Usar KV para dados pouco mutáveis (categorias, zonas de Luanda)
    - Rate limiting já implementado (100 req/min por IP) — manter
    - Respostas JSON pequenas
  O QUE SE ALCANÇA: Mais requisições cabem nos 100k/dia porque cada request
  custa menos CPU.
