RESUMO EXECUTIVO — O QUE SE PODE ALCANÇAR NO PLANO GRATUITO
--------------------------------------------------------------------------------

O LadiesGo já roda na Cloudflare (Pages + Workers + D1 + WebSockets).
No plano Free, com os 18 skills oficiais instalados, é possível atingir:

  • 5.000 a 10.000 usuários ativos por dia (passageiras + motoristas)
  • 100.000 requisições HTTP/dia via Workers (API)
  • 100.000 escritas/dia no D1 (banco)
  • 5.000.000 leituras/dia no D1
  • Banda ilimitada no frontend (Pages)
  • WebSockets ilimitados em mensagens (apenas conexões contam como requests)
  • Zero taxa de saída de dados (R2)
  • 500 builds/mês no Pages

Gargalo principal: Workers (100k requests/dia) e D1 Writes (100k/dia).
Estratégia: maximizar WebSocket, cache KV, Durable Objects e práticas de Worker
leve para empurrar esse limite o mais longe possível.

SKILL 1: cloudflare — Descoberta de produtos e limites
--------------------------------------------------------------------------------

O QUE FAZ: Ajuda o agente a identificar quais produtos Cloudflare atendem a cada
necessidade e aponta para a documentação correta.

COMO APLICAR NO LADIESGO (FREE):
  • Mapear cada funcionalidade do app para o produto Cloudflare mais barato/grátis:
      - Frontend estático → Pages (banda ilimitada)
      - API backend → Workers (100k req/dia)
      - Banco → D1 (100k writes/dia, 5M reads/dia)
      - Cache de sessões → KV (100k reads/dia)
      - Fotos de perfil → R2 (10GB, zero egress)
      - WebSockets → Durable Objects (mensagens não contam como Worker req)
  • Evitar produtos pagos (Access, Stream, Images, Argo) enquanto estiver no free.

O QUE SE ALCANÇA:
  • Arquitetura 100% dentro do free tier, sem custo mensal.
  • Clareza sobre o que é grátis e o que começa a cobrar, evitando surpresas na fatura.

SKILL 2: wrangler — Deploy e gerenciamento de Workers, D1, KV, R2, Queues
--------------------------------------------------------------------------------

O QUE FAZ: CLI para deploy de Workers, execução de migrations D1, gerenciamento
de KV, R2, D1, Queues.

COMO APLICAR NO LADIESGO (FREE):
  • `wrangler deploy` — subir a API do LadiesGo para produção (conta nova).
  • `wrangler d1 migrations apply` — aplicar migrations incrementais no D1
    (NUNCA reimportar dump completo; isso esgotou a conta nova em out/2026).
  • `wrangler kv:key put` — cache de categorias de corrida (Económico/Conforto/Família).
  • `wrangler r2 bucket put` — upload de fotos de perfil das motoristas/passageiras.
  • `wrangler d1 execute` — consultas diretas no banco para debug.

O QUE SE ALCANÇA:
  • Deploy rápido e seguro sem tocar na conta antiga esgotada.
  • Banco D1 mantido enxuto (apenas o necessário), preservando as 100k writes/dia.
  • Fotos de perfil fora do D1 (R2), economizando espaço e writes do banco.

SKILL 4: durable-objects — Coordenação stateful, WebSockets, SQLite, alarms
--------------------------------------------------------------------------------

O QUE FAZ: Objetos duráveis com estado, WebSockets, SQLite embarcado, alarms.

COMO APLICAR NO LADIESGO (FREE) — CRÍTICO:
  • WebSocket de GPS da motorista (`/api/v1/drivers/live-geo`): mensagens não contam
    como Worker requests (contam no DO a 20:1). Isso economiza enormemente o limite
    de 100k Worker requests/dia.
  • WebSocket de estado da viagem (`/api/v1/trips/<id>/live`): atualizações em tempo
    real sem polling HTTP.
  • WebSocket de pedidos (`/api/v1/trips/requests-live`): motoristas veem novas
    corridas sem refresh constante.
  • SQLite embarcado no DO para estado local rápido, reduzindo leituras D1.

O QUE SE ALCANÇA:
  • Rastreamento ao vivo de centenas de motoristas sem esgotar Worker requests.
  • Chat em tempo real entre passageira e motorista "de graça" (mensagens WS não contam).
  • Menos polling HTTP = menos consumo do limite de 100k requests/dia.
  • Suporte a mais usuários simultâneos com o mesmo teto de 100k.

SKILL 6: workers-best-practices — Workers prontos para produção
--------------------------------------------------------------------------------

O QUE FAZ: Boas práticas para escrever Workers eficientes e seguros.

COMO APLICAR NO LADIESGO (FREE):
  • Manter Worker leve: menos de 10ms CPU time por request (limite free).
  • Evitar chamadas externas síncronas (ex: Nominatim) dentro do caminho crítico;
    fazer em background ou cachear.
  • Usar `cache` do KV para dados que não mudam (categorias, zonas de Luanda).
  • Rate limiting já implementado (100 req/min por IP) — manter e ajustar se necessário.
  • Respostas JSON pequenas e comprimidas.

O QUE SE ALCANÇA:
  • Mais requisições cabem nos 100k/dia porque cada request custa menos CPU.
  • Menor risco de esgotar o CPU time do Worker.
  • API mais responsiva para passageiras e motoristas em Luanda.

SKILL 7: workers-profiling — Perfil de CPU e hotspots
--------------------------------------------------------------------------------

O QUE FAZ: Identificar endpoints lentos e hotspots de alocação em Workers.

COMO APLICAR NO LADIESGO (FREE):
  • Perfil do endpoint `/api/v1/trips/incoming` (itera sobre viagens pendentes).
  • Perfil de `/api/v1/drivers/nearby` (calcula Haversine para cada motorista).
  • Perfil de `/api/v1/trips/request` (faz fetch para Nominatim reverse geocode).
  • Otimizar os 3 endpoints mais quentes para consumir menos CPU e menos D1 reads.

O QUE SE ALCANÇA:
  • Identificar exatamente onde o Worker está gastando CPU e quota.
  • Reduzir o custo por request, permitindo mais usuários dentro dos 100k/dia.
  • Evitar que um endpoint ruim esgote o dia inteiro de quota.

SKILL 8: web-perf — Auditoria Core Web Vitals (FCP, LCP, TBT, CLS)
--------------------------------------------------------------------------------

O QUE FAZ: Auditar desempenho do frontend (ladiesgo.pages.dev).

COMO APLICAR NO LADIESGO (FREE):
  • Auditar `ladiesgo-home.html` (~250 KB) — o ficheiro mais importante da app.
  • Garantir: FCP < 1.8s, LCP < 2.5s, TBT < 200ms, CLS < 0.1.
  • Otimizar imagens (logo.jpg, splash.jpg) — servir via R2 ou otimizar tamanho.
  • Minificar CSS/JS inline (sem build step, mas comprimir manualmente).
  • Carregar recursos estáticos com cache longo (imagens, SVG).

O QUE SE ALCANÇA:
  • Página carrega rápido mesmo em conexões móveis de Luanda.
  • Menos abandono na landing page = mais cadastros na lista de espera.
  • Melhor experiência = mais usuários ativos/dia dentro do mesmo limite de API.
